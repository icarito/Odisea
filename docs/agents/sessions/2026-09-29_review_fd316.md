## Bugs de corrección (por severidad)

1. **ALTA — Input del handheld queda "pegado" ante pérdida/pausa de paquetes UDP.**
   `RemoteSimHost._apply_sim_input_entry` (RemoteSimHost.gd:288-294) guarda el último
   `_client_input_state` y `_apply_authority_input_frame` (:311-350) lo re-inyecta **cada
   tick** hasta que llegue otro paquete: no hay secuencia, timestamp ni vencimiento.
   Escenario: corte de WiFi de 1-2 s con el handheld caminando/sprinteando → el último
   axes/buttons sigue inyectándose tick a tick y el personaje corre a ciegas; un
   release perdido deja el sprint/jump pegado hasta el próximo paquete.

2. **ALTA (gameplay) — Flancos críticos viajan en un único datagrama sin redundancia.**
   El flanco de jump/interact y los deltas de cámara viajan solo por UDP
   (`RemoteSimClient._send_local_input`, RemoteSimClient.gd:236-267). Si el paquete del
   press se pierde y el siguiente ya trae `false`, el tap desaparece: la puerta no abre,
   el salto no salta. El host ya deriva el flanco por transición de estado
   (RemoteSimHost.gd:338-341), así que repetir el press 2-3 paquetes es seguro; o usar
   el WS que ya existe para esto.

3. **MEDIA — Paquetes duplicados duplican el look (no hay dedupe).**
   `_accumulate_client_camera` (RemoteSimHost.gd:298-303) suma sin identificador de
   paquete: dos copias del mismo datagrama (común en WiFi) suman doble el giro/zoom.
   Con número de secuencia se dedupea gratis (mismo fix que #1).

4. **MEDIA — Nodos spawneados durante el offload no se congelan (doble simulación
   residual).** El congelado corre una vez por escena (`_freeze_local_simulation`,
   RemoteSimClient.gd:137-149 en HEAD; ahora SimLogicFreeze.gd). Todo lo que entre al
   nivel DESPUÉS del primer snapshot (spawners, PlateContentStream, pickups) corre su
   `_physics_process` local encima de los snapshots: con PhysicsServer apagado no hay
   física, pero sí lógica GDScript (timers, streaming) divergiendo de la autoridad y
   gastando el CPU que el offload debía liberar.

5. **MEDIA — No hay semántica de pausa en offload.** El usuario del handheld abre su
   menú de pausa: `RemoteSimClient` es PROCESS (cuelga de RemoteControlManager
   PROCESS, RemoteControlManager.gd:55) → sigue aplicando snapshots y mandando el
   input del provider (el Input singleton no se pausa) → la simulación en la autoridad
   sigue con el mundo vivo detrás del menú. `host_paused` (:284-290) solo avisa al
   control; nadie pausa el sim del lado esclavo. La exención del sim host
   (PauseManager.gd:126-135, sin test) es el lado contrario y sí está decidida.

6. **MEDIA-BAJA — Re-promoción pisa la pose viva de la autoridad con
   `restore_snapshot`.** `_reuse_sim_level_if_same` (RemoteSimHost.gd:135-142) siempre
   re-aplica `_apply_spawn_state(hello)`: en `connection_lost` el handheld recupera su
   simulación local (`_stop_render_slave_role` → thaw) y el jugador puede haber seguido
   moviéndose; al retomar, la autoridad se teletransporta a la pose capturada del
   handheld con velocity reseteada. Con el freeze del stop blando [en curso] la
   autoridad ya no diverge, pero el re-sync incondicional sigue ahí; considerar
   aplicar el spawn solo si hay divergencia real.

7. **BAJA — Fallo de `start_render_slave` ignorado.** `_start_render_slave_role`
   (RemoteControlManager.gd:187-201) setea `is_render_slave_active=true` y manda las
   directivas aunque `start_render_slave` devuelva false (puerto sim ocupado):
   autoridad simulando para un esclavo sordo y sin input. Guardar el bool.

8. **BAJA — `PhysicsServer.set_active(true)` incondicional** al salir del rol
   (`_restore_local_physics`, RemoteSimClient.gd:173-174): re-prende el server aunque
   otro sistema lo haya apagado a propósito (p.ej. la sonda `split_load_frame` de
   SceneManager). Guardar/restaurar el estado previo.

9. **BAJA — Doble lectura del provider en el tick de transición** (arranque del nivel
   o reanudación): el player consume `provider.get_input()`
   (PlayerControllerV2.gd:3529) antes del primer frame inyectado; un flanco apretado en
   ese tick exacto se aplica dos veces (provider + frame inyectado). Ventana de 1
   tick; relevante solo para el rehearsal con oráculo.

## Riesgos de red

- **Sin auth en el canal UDP**: `sim_input` no valida token ni origen
  (RemoteSimHost.gd:270-276); el cliente no valida el token del snapshot; además
  `start_simulation(target_ip, port)` (RemoteControlManager.gd:244) descarta el token
  (el sim_hello sí lo lleva vía `server._active_token`, :222 — acceso privado entre
  instancias), así que `RemoteSimHost._token` queda "". Cualquier peer LAN puede
  inyectar input o suplantar snapshots; `_poll_udp` además fija `_target_ip` desde
  cualquier snapshot recibido (RemoteSimClient.gd:296-299) — spoofable.
- **Puertos**: sim = sensor+1 (RemoteControlManager.gd:191). Si el sensor migró de
  puerto por conflicto, sim puede chocar; el fallo solo hace printerr (ver bug 7).
- **Orden/dedupe**: la clave de cola es `last_tick` del cliente (tick aplicado, no
  secuencia del paquete): sirve para latest-wins, no para dedupe ni medir pérdida.
- **Tamaño**: snapshot JSON completo (entidades + rig de 5 transforms + estados ricos
  + cam_t) a 60 Hz sin delta ni compresión: riesgo de fragmentación IP en WiFi, que
  retroalimenta los bugs 1-3. Medir KB/s en el ensayo de stress (objetivo del FD).
- **Reconexión**: soft stop conserva tick y nivel [en curso, bien]; `_input_queue` y
  `_client_interact_was_down` sobreviven a la sesión; `start_simulation` re-bindea el
  socket (paquetes en vuelo perdidos — tolerable).
